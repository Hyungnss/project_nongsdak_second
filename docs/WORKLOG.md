- 없는 아이디로 로그인할 때도 해시를 한 번 계산한다. 바로 돌려주면 응답 속도로 아이디가 있는지 드러난다.

## 2026-09-02 · KAMIS 실시간 전환 마무리 (7단계 + 보류했던 결정 3건)

이 날 이전 상태: 2~6·8·9단계는 끝났고 **7단계(스케줄러)만 미착수**.
수동으로 `06` 을 돌리면 DB 가 갱신되지만 자동으로는 돌지 않았다.
그리고 **한 번 구현했다가 되돌린 보류 결정이 3건** 있었다.

**결과: 1~9단계 전부 완료. 매일 18:00 에 저절로 갱신된다.**

### 1. `06_upsert_daily_price.py` — `--days N` 추가

하루 한 번 실행은 **그날 날짜만** 요청한다. 실행을 한 번 놓치면 그날은 영영 빈칸이다
(다음날 실행은 어제가 아니라 오늘을 요청하므로). 노트북을 꺼 둔 날이 그대로 구멍이 된다.

`--days 3` 이면 오늘·어제·그저께를 함께 받아 구멍을 메우고, 덤으로 KAMIS 의 사후 개정도
따라간다. MERGE 라 다시 받아도 중복되지 않고 값만 최신이 된다.

- 인자 파싱을 새로 짰다. 기존 `[a for a in argv if not a.startswith("--")]` 방식으로는
  **`--days 3` 의 `3` 이 조사일 인자로 잡힌다.** 앞에서부터 훑도록 `parse_args()` 를 만들었다.
- 날짜별 소계 + 전체 합계로 출력을 나눴다 (`run_day()` 로 분리).
- 로그가 한 파일에 계속 쌓이므로 실행마다 `===== 시각 =====` 구분선을 넣었다.

> **주말 대응이 아니다.** 토·일은 며칠 뒤에 다시 받아도 축산물 29행 그대로다.
> KAMIS 가 조사를 안 한 날이라 애초에 자료가 없다. 연휴 대응은 아래 2번이다.

### 2. `webservice/db.py` — `TOLERANCE[1]` 6 → 11

`TOLERANCE[1]` 이 6 이면 **조사일 간격이 7일을 넘을 때 `_compare_all` 이 모든 품목을 버린다.**
6일 이상 연휴 다음 첫 조사일에 급등락·등락 요약·티커·포춘쿠키가 통째로 빈다
(품목별 상세는 정상이라 눈에 잘 안 띈다).

**11 로 올려 10일 연휴(조사일 간격 11일)까지 견디게 했다.**
철 지난 품종이 섞일 걱정은 없다 — 그건 `_compare_all` 의 `max_stale`(3일)이 따로 거른다.

### 3. 7단계 — `run_fetch.bat` + 작업 스케줄러 `KAMIS_fetch_1800`

**매일 18:00 · `--days 3`.** 계획서 초안의 12:00/16:00/18:00 세 번은 폐기했다 —
KAMIS 공표가 17:00 이라 그 전 두 번은 축산물만 받아 오는 헛돈이다.

옵션을 그렇게 준 이유:

| 옵션 | 왜 |
|---|---|
| `-StartWhenAvailable` | 18:00 에 PC 가 꺼져 있으면 그날이 통째로 날아간다. 켜지면 따라잡게 한다 |
| `-AllowStartIfOnBatteries` · `-DontStopIfGoingOnBatteries` | 기본값이 **배터리면 시작 안 함 / 배터리로 바뀌면 중단**이다. 노트북에서 이게 그대로 결번이 된다 |
| `-MultipleInstances IgnoreNew` | 앞 실행이 안 끝났는데 또 뜨는 걸 막는다 |
| `-Execute "cmd.exe" -Argument "/c ..."` | `.bat` 을 직접 Execute 에 넣는 것보다 실행 경로가 확실하다 |

### 4. 검증

| 확인한 것 | 결과 |
|---|---|
| `--days 3` dry-run | 3일치 543행 · DB 안 건드림 |
| 실제 적재 | 543행 반영 · DB **45,725 → 45,909행** · 최신 조사일 2026-09-02 |
| `TOLERANCE` 수정 후 화면 로직 | 94개 품목 비교 · 급등락 정상 |
| `run_fetch.bat` 직접 실행 | exit 0 · 로그 정상 |
| **작업 스케줄러 실행** (16:59) | **정상 완주 · 09-02 당일가격 29 → 176건** |
| 웹서비스 | `/`·`/api/meta`·`/api/products`·`/api/movers` 전부 200 · 09-02 기준 |

`/api/meta` 의 최신성 표시가 `TBL_FETCH_LOG` 를 읽어
`status=OK · age_minutes=9 · stale=False` 로 뜬다 — 8단계 화면 표시와 자동 수집이 붙었다.

### 겪은 문제와 원인

**① 배치 파일에 한글을 넣으면 깨진다.**
`cmd` 는 `.bat` 을 **그때그때의 콘솔 코드페이지**로 읽는다 (개발 셸 65001, 작업 스케줄러 949).
한글이 한 글자라도 들어가면 — `rem` 줄 안이라도 — 파서가 바이트 위치에서 어긋나
그 뒤 줄이 통째로 깨진다. 실제로 `'THONUTF8' is not recognized` 로 터졌다.
중간에 `chcp 65001` 을 넣는 것도 같은 이유로 안 된다 (오히려 그게 어긋남을 만든다).
→ **`run_fetch.bat` 은 주석까지 ASCII 로만 쓴다.** 한글 설명은 이 문서들에 둔다.
로그를 UTF-8 로 남기는 건 `PYTHONUTF8` · `PYTHONIOENCODING` 두 줄이 맡는다.

**② 실행 중에 작업 상태를 들여다보면 그 실행이 죽는다.**
다른 셸에서 `Get-ScheduledTask` 로 폴링하면 그 실행이 `0xC000013A`(^C)로 종료된다.
아무 일도 안 하는 `cmd /c echo` 진단 작업조차 같은 증상이었다.
**작업 자체의 결함이 아니다** — 아무도 안 볼 때 돌린 16:59 실행만 `^C` 없이 완주했다.
→ **상태 확인은 실행이 끝난 뒤에 한다.** 검증은 `logs\fetch.log` 로.

**③ 죽은 실행은 로그를 한 줄도 안 남긴다.**
파이썬 출력이 파일로 갈 때 블록 버퍼링되므로, 강제 종료되면 쌓아둔 출력이 통째로 날아간다.
17:01 실행은 `TBL_FETCH_LOG` 에는 기록을 남겼지만 `fetch.log` 에는 헤더조차 없었다.
→ 미조치. 아래 '남은 것' 참조.

### 결정 사항

| 항목 | 결정 | 비고 |
|---|---|---|
| `--days N` | **3** | 되돌렸던 것을 다시 붙였다 |
| `TOLERANCE[1]` | **11** (10일 연휴) | 되돌렸던 것을 다시 고쳤다 |
| **인증키 재발급** | **하지 않는다** | `--probe` 에 한 번 노출된 건. 마스킹만 고치고 지금 키를 계속 쓴다. **다시 제안하지 말 것** |

인증키는 이상 징후가 보일 때만 재검토한다 — 안 돌린 시각의 수집 기록, 호출 한도 오류.
둘 다 `TBL_FETCH_LOG` 에 드러난다.

### 남은 것

- **`run_fetch.bat` 의 파이썬 호출에 `-u`(무버퍼) 추가** — 위 ③ 때문. 로그가 유일한 감시
  창구라 붙여 둘 만하다. 제안만 하고 아직 안 했다.
- **배포** — 7단계까지 끝나도 이 PC 가 켜져 있을 때만 돈다. 로컬 Oracle XE 도 마찬가지다.
  남이 접속하려면 서버·DB 이전이 필요하다.
