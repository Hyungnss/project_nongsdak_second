# LightGBM 1차 튜닝 (2026-11-20)

> 결과만 보려면 [ML.md](ML.md) 의 '한눈에 보기'. 이 문서는 **어떻게 튜닝했고 설정마다 어땠는지** 전부를 남긴다.

---

## 1. 튜닝이 뭔가

base 모델(**LightGBM A** — 가격 정보만 넣은 LightGBM)에 **넣는 정보는 그대로 두고, 학습 설정만 바꿔서** 더 잘 맞히게 하는 것.
설정(하이퍼파라미터)은 모델이 데이터에서 스스로 배우는 값이 아니라, 사람이 학습 전에 정해 주는 값이다 —
'나무를 얼마나 복잡하게 만들지', '얼마나 천천히 배울지' 같은 것.

## 2. 설정 하나를 평가하는 방법

**실제 운영을 흉내 낸다** — 그 시점에 알 수 있던 정보로만 학습하고, 그 뒤를 예측하고, 나중에 나온 실제 가격으로 채점한다.

```
검증 기간 2022-10-15 ~ 2024-10-14 (2년)
│
├─ 2022-10-15 시점: 그때까지 '정답이 이미 나온' 과거 자료(2016~)로만 학습
│     → 그 뒤 28일 동안 매일, 품종마다 1 · 2 · 4주 뒤 가격 예측
├─ 28일 뒤: 그 사이 정답이 나온 자료를 더해 다시 학습
│     → 다음 28일 예측
├─ ...  (2년 동안 27번)
└─ 끝: 모든 예측을 실제 가격과 비교해 채점
```

- 미래 정보는 절대 쓰지 않는다 (누수 방지 시험 — `tests/test_ml.py`).
- 설정만 다르고 나머지(자료 · 기간 · 특성 · 채점)는 전부 같다 → 점수 차이 = 설정의 효과.

## 3. 점수

1. 품종마다 **MASE** = 모델 오차 ÷ '가격이 그대로일 것'(naive) 의 평소 오차. **1보다 작으면 naive 보다 잘 맞힌 것.**
2. 품종들의 **가운데 값(중앙값)** 을 1주 · 2주 · 4주 각각 구한다 (몇몇 품종의 큰 오차에 끌려가지 않게).
3. **점수 = 그 셋의 평균. 낮을수록 좋다.**

같이 보는 값: MAPE(평균 % 오차) · DIR(오를지 내릴지 맞힌 비율) — 점수가 좋아져도 이 둘이 나빠지면 다시 본다.

## 4. 왜 검증과 시험을 나누나

| 구간 | 기간 | 쓰임 |
|---|---|---|
| 학습 | 2016-01 ~ 그 시점 | 모델이 배우는 자료 |
| **검증** | 2022-10 ~ 2024-10 | **설정을 비교하고 고르는 곳** (이 문서의 모든 결과) |
| **시험** | 2024-10 ~ 2026-10 | **고른 설정을 마지막에 한 번만 채점하는 곳** |

여러 설정 중 점수가 제일 좋은 것을 고르는 순간, '그 기간에 우연히 잘 맞은' 설정이 뽑힐 수 있다.
그래서 고르는 것은 검증 기간에서, 실력 확인은 한 번도 안 본 시험 기간에서 한다 — **시험 문제를 미리 보고 공부하지 않는 것**과 같다.

## 5. 1차에서 바꿔 본 설정

**한 번에 하나만** 바꾼다 — 무엇이 효과 있는지 따로 보인다. 효과 있던 것끼리 2차에서 합친다.

먼저 LightGBM 이 예측하는 방식: '질문을 이어 가는 나무' 를 수백 개 쌓는다.

```
              최근 2주에 10% 넘게 올랐나?
               /                    \
             예                      아니오
             /                          \
    지금이 11~12월인가?              변동성이 큰가?
       /        \                     /        \
   [잎: -3%]  [잎: -1%]          [잎: +1%]   [잎: 0%]
```

질문을 따라 내려가 도착한 칸이 **잎** — '이런 상황이면 가격이 몇 % 변한다' 는 답이 들어 있다.

| 이름 | 바꾼 설정 | 기본 → 바꾼 값 | 뜻 · 기대 |
|---|---|---|---|
| `base` | — | — | 지금 설정 그대로 (비교 기준) |
| `leaves15` · `leaves31` · `leaves127` | `num_leaves` (잎 개수) | 63 → 15 · 31 · 127 | 나무 하나가 상황을 **몇 갈래까지** 나누나. 적으면 단순 · 안정, 많으면 세밀하지만 우연한 패턴까지 외울 위험(과적합) |
| `mcs50` · `mcs300` · `mcs1000` | `min_child_samples` (잎 최소 사례 수) | 100 → 50 · 300 · 1000 | 과거 사례가 **최소 이만큼 있어야** 잎을 만든다. 작으면 드문 상황도 배움, 크면 충분히 반복된 패턴만 배움 |
| `slow` | `learning_rate` × `n_estimators` (학습 속도 × 나무 수) | 0.05 × 400 → 0.02 × 1000 | 한 번에 조금씩, 더 여러 번 배운다 ('조금씩 여러 번 복습'). 보통 조금 정확해지고 2~3배 느리다 |
| `huber` | `objective` (오차 세는 방식) | l1 → huber (alpha 0.1) | l1 은 틀린 만큼만 벌줌(폭등 · 폭락에 강함). huber 는 작은 오차는 더 섬세하게, 큰 오차는 l1 처럼 |

공통: CPU 8개 (공용 Mac Studio 에서 실행 — 이 PC 는 메모리 7.7GB 로 학습 중 멈췄다).

## 7. 해석

**한 줄 결론: 기본 설정(base)이 이미 이 데이터에 잘 맞는다.** 9개 중 두 시장 모두에서 base 를 확실히(0.005 넘게) 이긴 설정이 없다.

| 설정 | 도매 | 소매 | 해석 |
|---|---|---|---|
| 잎 개수 (leaves) | 63 이 최고 | 63 이 최고 | 15 → 31 → 63 으로 늘릴수록 좋아지다 127 에서 다시 나빠진다. 적으면 패턴을 놓치고, 많으면 우연한 패턴까지 외운다. **기본값 63 이 딱 맞다** |
| 잎 최소 사례 수 (mcs) | 50 · 100 비슷, 300 · 1000 나쁨 | 같음 | 크게 하면 **1주가 나빠진다** (도매 1.183 → 1.224). 짧은 예측엔 드문 상황까지 세밀하게 보는 게 필요하다. 도매 4주만은 300 이 조금 좋았다(0.973 → 0.967) |
| 천천히 많이 (slow) | **-0.005 (유일하게 좋아짐)** | +0.001 (같음) | 도매에선 2주가 1.050 → 1.037 로 좋아졌지만 소매에선 효과 없음. 두 시장 모두 좋아야 믿는다는 기준엔 못 미친다 |
| 오차 방식 (huber) | +0.025 | +0.033 (꼴찌) | 특히 **1주가 크게 나빠진다** (도매 1.183 → 1.249). 평소 작은 오차에 맞추다 가끔 튀는 가격에 흔들린다. **l1 이 이 데이터에 맞다** |

- **어떤 설정이든 blend 보다 훨씬 낫다** (도매 1.194 · 소매 1.342 대비 6~11%). 모델이 기준선을 이기는 건 설정 덕이 아니라 가격 특성 덕이다.
- 설정을 바꿔서 얻는 차이(±0.03)는 **입력 · 모델 구조를 바꿔서 얻는 차이**(blend → LightGBM, 0.1 이상)보다 훨씬 작다.
- 'mcs 를 키우면 1주는 나빠지고 4주는 좋아진다' → **기간마다 다른 설정(기간별 모델)** 이 나중에 해 볼 만하다.

## 8. 다시 돌리기

```
uv run --group ml python -m ml.tune --cache-only               # DB → ml_runs/cache (한 번, Docker 필요)
uv run --group ml python -m ml.tune --round 1 --n-jobs 8       # 도매 · 소매, 1차 9개 (DB 없이 돈다)
```

결과: `ml_runs/tune/valid_r1_<market>.csv` · MLflow 실험 `price-tuning-wholesale` · `price-tuning-retail` (run 이름 `r1:<설정>`).
