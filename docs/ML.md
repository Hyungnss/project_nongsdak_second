# 가격 예측 모델 (ml/)

KAMIS 일별 가격으로 **품종별 1주 · 2주 · 4주 뒤 가격**을 예측한다.
학습 · 실험은 PC 에서만 하고(`uv sync --group ml`), 서버 이미지에는 들어가지 않는다.

```
uv run --group ml python -m ml.run --market 도매 --models baselines      # 기준선 6종
uv run --group ml python -m ml.run --market 도매 --models naive,blend,lgbm
uv run --group ml mlflow ui --backend-store-uri sqlite:///ml_runs/mlflow.db
```

| 파일 | 하는 일 |
|---|---|
| `ml/dataset.py` | DB → 품종별 일별 시계열 → 예측 표본 (기준일 · 기간 · 목표일 · 정답) |
| `ml/baselines.py` | 기준선 — 학습 없이 규칙으로 예측 |
| `ml/features.py` | LightGBM 특성 (가격에서만 만든다) |
| `ml/backtest.py` | 시간 순서를 지키는 백테스트 · 지표 |
| `ml/run.py` | 실행 → 결과표 → MLflow 기록 |
| `tests/test_ml.py` | 목표일 규칙 · 지표 · **누수 방지** 시험 |

## 2. 전처리

가격만 쓰는 base 모델이라 전처리는 '쓸 데이터 고르기 · 비율로 바꾸기 · 빈 값은 그대로' 가 전부다.
DB 의 원본은 어느 단계에서도 고치지 않는다 — 전처리는 학습 데이터를 만들 때만 한다.

### 한 것

| 단계 | 처리 | 코드 |
|---|---|---|
| 대상 고르기 | 가격이 있는 날만 (0원 · 빈 값 제외 — DB 가 0 을 막고 수집기가 NULL 로 넣는다) | `dataset.load_series` |
| | 품종마다 대표 등급 하나 (`db.list_products` — 상품 우선, 최근 90일 관측이 20번 미만인 등급은 뒤로) | 〃 |
| | 관측이 60일 미만인 품종은 뺀다 | `dataset.frame_to_series` |
| 빈 날 | 주말 · 공휴일을 메우지 않는다. 시계열을 '조사한 날' 만으로 이어 붙인다 | 〃 |
| 크기 맞추기 | 모든 특성을 **로그 비율**로 만든다. 쌀(5만 원)과 깻잎(2천 원)을 같은 눈금으로 | `features.build` |
| | 맞히는 값도 `log(미래 가격 / 기준일 가격)` | `features.target` |
| 결측 특성 | 과거가 짧아 못 구한 특성(작년 값 없음 등)은 NaN 그대로 — LightGBM 이 직접 다룬다 | `features.build` |
| | 0 으로 나눠 생긴 무한대는 NaN | 〃 |
| 범주 | 품목 · 부류는 범주형 | 〃 |

### 하지 않은 것

| 안 한 것 | 이유 |
|---|---|
| 이상값 제거 · 상한 자르기 | 품질 점검(`collector/quality.py`)에서 도매 단위 변경 · 하루 튐 0건. 남은 '시장 변화' 13건(생강 · 팥 · 들깨 · 양파 · 당근)은 실제 가격 흐름이라 모델이 배워야 한다 |
| 표준화 (평균 0 · 분산 1) | 트리 모델은 값의 크기에 영향받지 않는다. 품목 간 크기는 비율로 맞췄다 |
| 빈 날 채우기 | 조사일만 이어 붙여 필요 없다 |
| 계절 품종 잇기 | 배추 가을 · 월동 등은 별개 시계열. 철이 바뀔 때 예측이 끊기는 한계 (과제) |
| 날씨 · 물가 | base 모델은 가격만 쓴다. 아래 '③-1 에서 할 전처리' 참고 |

### 주의 — 백필 행의 빈 열

과거 백필 행(`DATA_SOURCE='kamis_period'`)에는 당일가격 · 평년가격만 있고 1일전 · 1주전 · 1년전 가격 열은 비어 있다.
특성은 이 열을 쓰지 않고 **가격 시계열에서 직접 계산**한다 (작년 값도 364일 전 조사일을 찾아 쓴다). 새 특성도 이 원칙을 지킨다.

### ③-1 에서 할 전처리 (날씨 · 물가를 넣을 때)

| 데이터 | 처리 | 근거 |
|---|---|---|
| 날씨 | 김해시 평균기온 2건(평균이 최저~최고 밖)은 빈 값으로 | 품질 점검 '범위 밖 값' |
| | 관측소 결측 1~3일(8곳)은 앞뒤 값으로 | 품질 점검 '빠진 날' |
| | 일사량은 측정 관측소(67곳)만 쓰거나 제외 | 절반이 빈칸 |
| | 관측소 → 산지 · 시도별로 묶기 | |
| 물가 | 월 값을 일별 표본에 붙일 때 `AVAILABLE_AT <= 기준일` 인 것만 | 발표 전 값을 쓰면 누수 |
| 공통 | 모든 외부 특성은 `AVAILABLE_AT` 기준으로 그 시점에 알 수 있던 값만 | |

## 3. 기준선 (확정: `blend`)

'이것도 못 이기면 모델이 필요 없다' 는 바닥선. 학습 없이 규칙으로 예측한다.

| 이름 | 예측 |
|---|---|
| `naive` | 기준일 가격 그대로 |
| `seasonal_naive` | 목표일 364일 전(같은 요일) 가격 |
| `seasonal_adjusted` | 기준일 가격 × (작년 목표일 / 작년 기준일) |
| `moving_average` | 최근 20 조사일 평균 |
| `seasonal_profile` | 기준일 가격 × 예년 계절 모양(목표일) / 예년 계절 모양(기준일). 모양은 4주마다 그 이전 자료로 다시 만든다 |
| **`blend`** | **`naive` 와 `seasonal_profile` 의 평균** |

**blend 는 '예년 계절 변화의 절반만큼 바뀐다' 는 규칙이다.**
```
오늘 3,000원, 예년엔 4주 동안 20% 내림
  naive            3,000원
  seasonal_profile 3,000 × 0.8 = 2,400원
  blend            (3,000 + 2,400) / 2 = 2,700원   (10% 내림)
```

**왜 blend 인가** (도매, 4주 뒤 MASE 중앙값 — 낮을수록 좋음)

| 부류 | naive | seasonal_profile |
|---|---|---|
| 채소 · 과실 | 0.974 · 1.300 | **0.837 · 1.213** — 제철이 뚜렷하다 |
| 곡물 · 특용 · 수산 | **0.781 · 0.949 · 1.660** | 1.213 · 1.049 · 1.983 — 저장 · 수입 품목은 계절을 덜 탄다 |

강점이 부류마다 갈려서, 둘을 섞으면 어느 쪽에서도 크게 틀리지 않는다.
1 · 2 · 4주 모두 6종 중 가장 좋거나 거의 같았다 (도매 4주 뒤 0.910 · 소매 1.071). 모델은 이 점수를 넘어야 한다.
도매 1주 뒤만 naive(1.044)가 blend(1.047)보다 0.3% 나은데, 사실상 같은 수준이라 기준선은 blend 로 둔다.

**계절 모양 기준 변경 (2026-11-20)** — 계절 프로파일은 '그 해 평균' 으로 나눈 비율을 쓰는데, 처음엔 한 해에
100일 이상 조사된 해만 썼다. 가을 배추처럼 철에만 조사되는 품종(한 해 30~48일)은 모든 해가 탈락해 계절 모양을
못 만들고 '가격 그대로' 로 메워졌다 (서비스에서 배추 예측이 +0.0% 로 나와 발견). 기준을 **20일**로 낮춰
(`baselines.PROFILE_MIN_OBS`) 메운 표본이 도매 7.7% → 2.6% · 소매 10.3% → 4.7% 로 줄었고, 정확도는 거의 같다
(도매 4주 0.933 → 0.910, 1 · 2주 0.009 · 0.014 나빠짐 / 소매 1 · 2 · 4주 모두 조금 좋아짐).
위 부류별 표는 바꾸기 전(100) 실행이다.

## 4. base 모델 — LightGBM (가격만)

- **모든 품종을 모델 하나로** 학습한다 (배추에서 배운 패턴을 무에도 쓰게).
- 특성 16개 — 최근 5 · 20 · 60 조사일 평균 대비 위치, 5 · 20 · 60 조사일 수익률, 20 조사일 변동성,
  직전 조사일과의 간격, 작년 · 재작년 같은 기간 변화, 작년 대비 수준, 평년가 대비 수준,
  목표일의 연중 위치(sin · cos) · 요일, 예측 기간, 품목 · 부류
- 설정은 기본값 (`backtest.LGBM_PARAMS`). 시험 기간 결과를 보며 설정을 고치면 점수가 부풀려지므로 아직 튜닝하지 않았다.

## 5. 평가 — 시간 순서를 지키는 백테스트

무작위로 섞어 나누면 미래로 과거를 맞히게 된다. 그래서 **학습은 항상 과거, 시험은 그 직후 4주**로 나누고
4주씩 앞으로 옮기며 반복한다 (walk-forward).

```
1번째:  [ 학습: 2016-01 ~ 2024-10-13 ] → [ 시험: 2024-10-14 ~ 11-10 ]
2번째:  [ 학습: 2016-01 ~ 2024-11-10 ] → [ 시험: 2024-11-11 ~ 12-08 ]
  ...                                          (4주씩 앞으로, 27번)
27번째: [ 학습: 2016-01 ~ 2026-09-15 ] → [ 시험: 2026-09-16 ~ 10-14 ]
```

- 시험 기간은 최근 2년 (최신 조사일 - 35일까지 — 4주 뒤 정답이 있어야 채점한다). 학습은 매번 2016년부터 그 시점까지 전부.
- 학습에는 **그 시점에 정답이 이미 나온 표본만** 쓴다 (목표일 < 재학습 날짜).
- 튜닝을 시작하면 기간을 셋으로 나눈다: 학습 ~2022-10 · 검증(튜닝) 2022-10~2024-10 · 시험(최종 점수, 한 번만) 2024-10~2026-10.

**지표**

| 지표 | 뜻 | 쓰임 |
|---|---|---|
| **MASE 중앙값** | 오차 / 평가 이전 기간 naive 오차. 품종마다 구해 중앙값 | **주 지표**. 가격 크기와 상관없이 품종끼리 비교 |
| MASE 평균 | 같은 값의 평균 | 크게 틀리는 품종이 있는지 (고등어 같은 소수 품종에 끌린다) |
| MAPE | 평균 % 오차 | 사람이 읽기 쉬운 값 |
| DIR | 오를지 내릴지 맞힌 비율 | 화면의 '사기 좋은 때' |

**누수 방지** — 미래 가격을 일부러 10배로 바꿔도 기준일의 기준선 예측 · 특성이 그대로인지 `tests/test_ml.py` 가 확인한다.

## 6. 결과

### 도매 (117품종, 시험 2024-10-14 ~ 2026-10-14, 2026-11-19 실행)

| 기간 | MASE 중앙값 naive → blend → **LightGBM** | MAPE blend → LightGBM | DIR blend → LightGBM |
|---|---|---|---|
| 1주 | 1.044 → 1.047 → **0.995** | 5.2% → 5.0% | 59% → 61% |
| 2주 | 1.042 → 1.038 → **0.958** | 7.8% → 7.4% | 61% → 64% |
| 4주 | 1.081 → 0.910 → **0.864** | 11.0% → 10.1% | 64% → 67% |

부류별 (4주 뒤 MASE 중앙값, blend → LightGBM): 식량 0.943 → 0.716 (**-24%**) · 과실 1.265 → 1.018 (-20%) ·
채소 0.831 → 0.728 (-12%) · 특용 0.987 → 0.872 (-12%) · 수산 1.782 → 1.641 (-8%).
품종 116개 중 86개(74%)에서 LightGBM 이 더 나았다.

- 기준선이 약했던 곡물에서 가장 크게 좋아졌다. 품목마다 '계절을 얼마나 믿을지' 를 스스로 배운 것으로 보인다.
- **수산이 가장 어렵다** (냉동 고등어 · 홍합 · 마른김 · 마른오징어). 가격 흐름만으로는 안 보이는 수입량 · 어획량 ·
  환율의 영향이 큰 것으로 보인다 → ③-1 에서 물가(수산물 지수) 등 외부 특성의 효과를 볼 대상.

### 소매 (153품종, 시험 2024-10-15 ~ 2026-10-15, 2026-11-20 실행)

기준선 6종 중 **blend 가 1 · 2 · 4주 모두 1등** (MASE 중앙값 1.229 · 1.177 · 1.071, 연간 최소 조사일 20 기준).
소매는 도매와 달리 계절 프로파일 혼자서는 naive 보다 못하다(4주 1.174 vs 1.129) — 소매 가격이 덜 출렁여
예년 모양을 그대로 믿으면 과하다. '절반만 믿는' blend 가 더 잘 맞는 이유이기도 하다.

| 기간 | MASE 중앙값 blend → **LightGBM A** | MAPE | DIR |
|---|---|---|---|
| 1주 | 1.229 → **1.192** | 4.0% → 4.0% | 55% → 61% |
| 2주 | 1.177 → **1.102** | 5.5% → 5.3% | 57% → 63% |
| 4주 | 1.071 → **0.984** (-8%) | 7.1% → 6.7% | 60% → 65% |

4주 뒤 품종 152개 중 111개(73%)에서 A 가 blend 보다 나았다 (기준 변경 전 blend 와 비교). 부류별(4주, 같음): 과실 1.330 → 1.146 · 수산 1.381 → 1.178 ·
식량 1.189 → 1.067 · 축산 1.078 → 0.988 · 채소 0.831 → 0.777 개선, **특용작물만 1.213 → 1.247 로 나빠졌다**.

## 7. 외부 특성 실험 (③-1)

base 모델(A, 가격만)에 날씨 · 물가를 더해 효과를 본다. 같은 데이터 · 같은 백테스트 · 같은 LightGBM 설정에서
**입력만 바꾼다**. 코드는 `ml/external.py`, 누수 방지 시험은 `tests/test_ml_external.py`.

```
uv run --group ml python -m ml.run --market 도매 --models features            # A · B · C
uv run --group ml python -m ml.run --market 도매 --models lgbm,lgbm_region,lgbm_region_oracle   # A · D · E
```

| 이름 | 입력 | 쓰임 |
|---|---|---|
| A `lgbm` | 가격만 | 현재 가장 나은 조합 — **지금 기준의 서비스 후보** (실험에 따라 바뀔 수 있다) |
| B `lgbm_ext` | A + 전국 날씨(평년 차이 7 · 30 · 90일, 서리 · 폭염) + 물가(부류별 · 총지수, 전년 · 전월 대비) | 서비스에 쓸 수 있는 조합 |
| C `lgbm_oracle` | B + 예측 기간의 **실제 미래** 전국 날씨 | **실험용** — '예보가 완벽하다면' 의 상한선. 서비스에는 못 쓴다 |
| D `lgbm_region` | A + **산지(시도) 날씨**, 시차 30 · 90 · 180일 | 실험 2 |
| E `lgbm_region_oracle` | D + 산지의 실제 미래 날씨 | 실험용 |

**누수 방지** — 날씨는 기준일 전날까지(일자료는 다음 날 나온다), 평년은 그 해 이전 해들로만,
물가는 기준일 17:30 이전에 발표된(`AVAILABLE_AT`) 달까지만. 미래를 바꿔도 특성이 그대로인지 시험한다.
날씨는 기온 자체가 아니라 **평년과의 차이**를 쓴다 — 계절은 이미 가격 특성에 들어 있어서다.

### 실험 1 — 전국 날씨 + 물가 (도매, 2026-11-20)

| 기간 | A 가격만 | B + 날씨 · 물가 | C + 완벽한 예보 |
|---|---|---|---|
| 1주 | **0.997** | 1.050 | 1.052 |
| 2주 | 0.960 | **0.955** | 0.964 |
| 4주 | 0.870 | **0.854** | 0.876 |

(MASE 중앙값) — B 가 A 보다 나은 품종은 1주 32% · 4주 45%. C 가 B 보다 나은 품종은 1주 48% · 4주 52%.

**결론: 효과가 없다.** 4주 뒤 전체 2% 개선은 절반 넘는 품종에서 나빠진 결과라 우연에 가깝다.
특성 중요도에서 날씨는 상위 15위 안에 없었고, 물가는 쓰였지만 성능을 올리지 못했다.

**'완벽한 예보' 조차 도움이 안 됐다** — 날씨가 쓸모없다는 뜻이라기보다 넣은 날씨의 모양이 틀렸다는 신호로 본다.
- **전국 평균이라서**: 고랭지 배추는 강원, 월동 배추는 해남 날씨가 중요한데 전국 평균에 묻힌다.
- **시차가 짧아서**: 날씨는 몇 달 뒤 수확량에 영향을 준다. 최근 90일 · 앞으로 4주로는 잡기 어렵다.
- **물가는 결과에 가깝다**: 농산물 물가 지수는 가격이 오른 결과라, 가격 특성에 이미 있는 정보를 늦게 다시 준다.

→ 지금까지는 **A(가격만)** 가 가장 낫다 (확정 아님). 원인을 확인하려고 실험 2(산지 날씨 · 긴 시차)를 하고, 그 결과에 따라 다시 고른다.

### 실험 2 — 산지 날씨 · 긴 시차 (도매)

품목(· 품종)마다 주산지 시도의 날씨를 붙인다 (`external.REGIONS`). 배추 · 무는 철마다 산지가 달라 품종별로 정했다
(고랭지 → 강원, 월동 배추 → 전남, 월동 무 → 제주). 수입 과일 · 버섯은 날씨와 무관해 붙이지 않는다.
**산지 연결표는 일반적으로 알려진 주산지로 정한 가정이다** — 통계청 시도별 생산량 등으로 확인할 것.

| 기간 | A 가격만 | D + 산지 날씨 | E + 산지의 완벽한 예보 |
|---|---|---|---|
| 1주 | **0.997** | 1.045 | 1.035 |
| 2주 | **0.960** | 0.979 | 0.981 |
| 4주 | 0.870 | **0.857** | 0.887 |

(MASE 중앙값) — 산지를 연결한 품종(73개) 중 D 가 A 보다 나은 품종은 1주 20% · 4주 36%.
E 가 D 보다 나은 품종은 1주 49% · 4주 60%. 고랭지 배추(강원) 4주 오차는 A 0.427 → D 0.539 로 오히려 커졌다.
특성 중요도에는 산지 날씨(180일 강수 · 60일 서리 · 180일 기온)가 처음 등장했지만 성능은 오르지 않았다.

**결론: 산지 · 긴 시차로 바꿔도 효과가 없다.**

### 두 실험을 합친 해석

- 전국이든 산지든, 날씨를 넣으면 대부분 품종에서 조금씩 나빠진다 — 1~4주 예측에서 날씨 특성은 잡음으로 작용한다.
- '완벽한 예보' 도 거의 도움이 안 된다 — **이미 지난 날씨는 지금 가격에 반영돼 있다**. 시장이 날씨 소식을
  가격에 담기 때문에, 가격 흐름만 봐도 1~4주 앞은 충분히 설명된다.
- 날씨가 힘을 쓰는 건 수확량이 정해지는 **몇 달 단위** 예측일 가능성이 크다.

→ 지금까지는 **A(가격만)** 가 가장 낫다 (확정 아님 — 아래 '다음' 의 실험에 따라 다시 고른다).

발표 · 포트폴리오용 한 줄: 외부 데이터를 두 방식(전국 · 산지)으로 넣고 완벽한 예보까지 실험했지만 1~4주 예측에는
도움이 안 됐다 — 지난 날씨는 이미 가격에 반영돼 있기 때문이다 (가설 → 실험 → 반증 → 해석).

### 소매에서도 같은 결론 (2026-11-20)

| 기간 | A 가격만 | B + 전국 날씨 · 물가 | C + 완벽한 예보 | D + 산지 날씨 | E + 산지 완벽한 예보 |
|---|---|---|---|---|---|
| 1주 | 1.192 | 1.197 | 1.190 | 1.191 | 1.181 |
| 2주 | 1.102 | 1.104 | 1.092 | 1.102 | 1.093 |
| 4주 | 0.984 | 0.973 | 0.968 | 0.983 | 0.984 |

(MASE 중앙값) — 차이가 1% 안팎이고, 품종별로 B 가 A 보다 나은 품종 1주 35% · 4주 42%, D 가 A 보다 나은 품종 35% · 39%.
도매와 같이 **외부 특성은 1~4주 예측에 효과가 없다**. 축산(소매에만 있다)도 물가 지수로 좋아지지 않았다(0.988 → 0.992).

## 8. 서빙 — 예측을 서비스에 올리기 (v2.5.0)

**기준선(blend)을 먼저 운영에 올리고, 더 나은 모델이 증명되면 교체한다.** 표 · API · 화면은 모델과 상관없이 같다.

```
매일 17:30  가격 수집 → 점검 → collector/predict.py  (ml/predict.py — blend)
            품종 · 등급마다 마지막 조사일 기준 7 · 14 · 28일 뒤 → TBL_PRICE_FORECAST
화면        GET /api/forecast?item&kind&rank&market            (backend/forecast.py — 화면과의 약속 모양)
공개 API    GET /api/v1/forecast  (키 필요, {data, meta}, meta.model · model_version)
평가        V_FORECAST_EVAL — 목표일의 실제 가격이 나오면 예측과 비교 (APE · 방향)
```

| 규칙 | 이유 |
|---|---|
| 기준일 = 그 품종의 마지막 조사일 | 주말 · 공휴일에도 가장 최근 가격에서 출발 |
| 시장 최신 조사일보다 7일 넘게 끊긴 품종은 예측하지 않는다 (빈 목록) | 철 지난 등급(예: 올해 조사 안 된 가을 배추 중품)에 1년 전 가격을 '예측' 으로 보여 주지 않게 |
| 계절 모양을 못 만들면 기준일 가격 그대로 + `FALLBACK` 표시 | 예측이 비지 않게 하되 메운 것인지 추적한다 |
| 예측마다 `MODEL` · `MODEL_VERSION` 저장 | 어떤 모델이 이 숫자를 냈는지 끝까지 추적 (교체 전후 비교) |

모델 교체 — `ml/predict.py` 의 `MODEL` · `MODEL_VERSION` 과 예측 함수를 바꾼다. LightGBM 으로 바꾸면 서버 이미지에
lightgbm(+ libgomp)과 모델 파일(버킷 `models/` + `current.json`)이 필요하다 (v2.6.0 계획).
